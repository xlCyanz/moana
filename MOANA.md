# MOANA — Especificación técnica

Versión del contrato: **0.1.20-draft** · Fecha: **2026-11-18** · Estado: especificación inicial para implementación; motor todavía no implementado.

Este archivo es la fuente de verdad del producto. «DEBE» expresa una condición verificable; «DEBERÍA», una recomendación artística o de diseño. Los contratos aquí descritos son objetivos futuros, no APIs disponibles en el paquete inicial. Los cambios de contrato requieren actualizar este documento, los ejemplos, los issues y una decisión de arquitectura cuando afecten compatibilidad. El catálogo de requisitos y su trazabilidad vive en `docs/requirements.json` y `docs/issues/traceability.md`.

## 1. Visión y objetivos

Moana será una biblioteca Python de dibujo programático de Pixel Art: un agente describe una escena estructurada, Python la valida y rasteriza, y el usuario puede pedir «cambia el color de la capa», «mueve el ojo izquierdo» o «suaviza esa silueta» sin reconstruir el resto del sprite mediante un modelo de generación de imágenes. El tamaño de referencia es 128 × 128; la resolución no determina por sí sola el estilo.

**Pillow y NumPy proporcionan las herramientas gráficas, pero no garantizan por sí mismos una calidad artística profesional.** La calidad dependerá de las instrucciones, los algoritmos, las técnicas de Pixel Art y los sistemas de evaluación implementados. Ningún puntaje automático sustituye la revisión visual del usuario o artista.

Objetivos: precisión de píxel, siluetas legibles, clusters intencionales, paletas coherentes, edición local explicable, capas recuperables, animaciones consistentes y resultados reproducibles. El agente debe poder mostrar el PNG resultante a escala nativa y ampliado mediante vecino más cercano, conservar el documento fuente y aplicar una revisión específica con un diff identificable.

## 2. Alcance funcional y no funcional

El producto cubre personajes, criaturas, objetos, tiles, escenarios y animaciones 2D. La primera entrega funcional cubrirá documentos estáticos con primitivas, paletas, capas, render RGBA y exportación PNG. Las entregas siguientes agregan máscaras, técnicas artísticas, edición persistente y animación. Una integración con IA consume el mismo contrato público que un programa Python; el núcleo no necesita un proveedor de IA ni acceso de red.

Fuera del alcance inicial: GUI de pintura, modelos generativos visuales, rasterización 3D, fotorealismo, fuentes del sistema, plugins ejecutables dentro de documentos, descarga automática de recursos, PSD/Aseprite de ida y vuelta y interpolación de movimiento aprendida. No se implementará el motor en la inicialización del repositorio.

Requisitos no funcionales: Python >=3.12; instalación como paquete; operaciones sin estado global mutable; entrada no confiable validada antes de reservar buffers; errores tipados; resultados verificables; documentación en español e identificadores de código en inglés. Se comprueba inicialmente Python 3.12–3.14 en CI; las versiones posteriores permitidas por metadata requieren ampliar esa matriz para declarar soporte verificado.

## 3. Arquitectura modular

Flujo obligatorio: `entrada → validación sintáctica → resolución de referencias → presupuesto → plan de render → máscaras/primitivas → composición → evaluación → exportación`. La edición transforma el documento validado y vuelve a entrar por esa misma ruta.

| Módulo futuro | Responsabilidad | Dependencias internas permitidas |
| --- | --- | --- |
| `core` | coordenadas, límites, errores, buffers y contratos | ninguna |
| `schema` | modelos Pydantic, discriminadores y JSON Schema | core |
| `palette` | colores, ramps, remapeos e índices | core |
| `geometry` | máscaras de primitivas y transformaciones | core |
| `layers` | árbol ordenado, máscaras y composición | core, palette, geometry |
| `techniques` | contornos, clusters, dithering y materiales | core, geometry, palette |
| `render` | resolución, plan, caché y ejecución determinista | core, schema, palette, geometry, layers, techniques |
| `editing` | comandos transaccionales e historial | core, schema |
| `project` | lectura/escritura, assets, migraciones | core, schema, editing |
| `animation` | timeline y evaluación de frames | core, schema, editing, render |
| `export` | PNG/GIF/WebP/APNG/spritesheets y manifiestos | core, palette; recibe resultados, no llama al editor |
| `quality` | métricas, incidencias y visualizaciones de diagnóstico | core, palette |
| `api` / `cli` | fachada y composición de servicios | módulos anteriores |

El orquestador combina render y quality; el rasterizador no depende del CLI, del almacenamiento ni del evaluador. Pillow, NumPy y AggDraw quedan detrás de adaptadores internos. Los contratos de dominio no exponen objetos mutables de esas bibliotecas. No se crean módulos vacíos simulando funcionalidad: se incorporan al comenzar su issue. La distribución expone la fachada `moana.api` y el comando estático `moana` (MOANA-012, ADR-020) sobre los módulos implementados; los módulos futuros no se publican hasta tener comportamiento real.

## 4. Stack tecnológico

Python 3.12+ es el lenguaje; Pillow provee buffers/intercambio y codificadores; NumPy, arrays y operaciones vectorizadas; AggDraw, un adaptador de trazados complementarios; Pydantic v2, validación estricta y generación de esquema. `uv` gestiona intérprete, entorno y lock real. Hatchling construye wheel/sdist. pytest y coverage verifican comportamiento; Hypothesis aporta propiedades; Ruff verifica estilo y formato; mypy aplica tipado estricto. PyYAML sólo forma parte del tooling de desarrollo para verificar skills y manifiestos.

`pyproject.toml` declara rangos compatibles y `uv.lock` fija las resoluciones concretas con hashes. CI sincroniza con `uv sync --locked`; las actualizaciones de dependencias generan cambios revisables del lock y regresiones. No se declara reproducibilidad de bytes entre versiones arbitrarias de codificadores. AggDraw puede carecer de stubs: su excepción de mypy se limita al import, y su adaptador tendrá superficie tipada y pruebas propias.

## 5. Motor de lienzo y píxeles

El origen es la esquina superior izquierda; x crece a la derecha y y hacia abajo. Un píxel se indexa `(x, y)` y se almacena `array[y, x, channel]`. El array canónico es C-contiguo, `uint8`, forma `(height, width, 4)`, RGBA recto (no premultiplicado). Color de trabajo sRGB codificado; la composición normativa usa esos valores enteros, sin conversión implícita a luz lineal. El color de todo píxel con alfa cero se normaliza a `(0,0,0,0)`.

Dimensiones válidas: 1–2048 por eje, con límite adicional de área de 4 194 304 píxeles. Predeterminado 128 × 128. Las coordenadas son enteros reales del JSON (no booleanos, strings ni floats); rango absoluto <=1 048 576. Una caja es `[x0,y0,x1,y1)`; exige x0<x1 e y0<y1. El rango absoluto se aplica a coordenadas de píxel; el borde excluido de una caja puede llegar a 1 048 577 para que todo píxel válido tenga caja 1 × 1. Una intersección o recorte sin píxeles es ausencia de caja, no una caja vacía (ADR-010). La geometría puede quedar fuera del lienzo: se recorta sin wraparound ni error, después de presupuestar su complejidad. Acceso directo a un píxel fuera del lienzo produce error de límites; no hereda índices negativos de NumPy.

Las vistas públicas son inmutables o copias; el propietario del buffer controla la vida útil. El lienzo y sus adaptadores NumPy/Pillow son submódulos de `core` que su paquete no importa; sólo intercambian copias e imágenes `RGBA` de un frame, sin convertir modos implícitamente (ADR-013). Se usan acumuladores uint32/int64 antes de multiplicar para evitar overflow. Escalado de preview sólo por factores enteros >=1 mediante vecino más cercano; el archivo de trabajo conserva la resolución original.

## 6. Geometría y primitivas

Cada operación tiene `id`, `type` discriminador y parámetros explícitos. La primera familia incluye `pixel`, `line`, `rect`, `ellipse`, `polygon` y, con el backend `aggdraw-v1` (MOANA-007, ADR-023), `path`; luego `flood_fill` y transformaciones. Las primitivas generan máscaras binarias, no colores intermedios por antialias automático.

| Operación | Parámetros específicos | Regla raster |
| --- | --- | --- |
| pixel | `at: [x,y]`, `color` | exactamente un píxel |
| line | `start`, `end`, `color` | Bresenham entero inclusivo en ambos extremos |
| rect | `box`, `color` | caja semiabierta, rellena |
| ellipse | `box`, `color` | inclusión del centro del píxel en elipse |
| polygon | `points` (>=3), `color` | even-odd, centros de píxeles, sin AA |
| path | `commands`, `color`, `backend` (`aggdraw-v1`) | relleno nonzero por cobertura AGG ≥128 a escala nativa; subpaths abiertos cerrados implícitamente |
| flood_fill | `at`, `color`, `connectivity: 4` | igualdad RGBA exacta sobre copia del estado anterior de la capa |

Para `line`, ordenar lexicográficamente los extremos antes del Bresenham simétrico: dx=abs(x1-x0), dy=-abs(y1-y0), err=dx+dy; calcular e2=2*err antes de cada paso; avanzar x si e2>=dy y avanzar y si e2<=dx. Esto fija empates y la simetría al invertir extremos. Grosor inicial: 1 píxel; los trazos gruesos se derivan de dilatación explícita, no de opciones variables de Pillow.

Para `ellipse`, w=x1-x0, h=y1-y0, A=2*x+1-x0-x1 y B=2*y+1-y0-y1; incluir si A²*h²+B²*w²<=w²*h². Usar enteros Python para esta evaluación o demostrar que el tipo elegido no desborda. Para `polygon`, descartar aristas horizontales en el cálculo de cruces; activar cada arista en `min(y0,y1)<=py<max(y0,y1)`, py=y+1/2; incluir un centro cuando el número de intersecciones estrictamente a su derecha sea impar. Las comparaciones se hacen con racionales/enteros. Se permiten autointersecciones bajo even-odd; vértices repetidos consecutivos se normalizan y una máscara es vacía sólo cuando no contiene centros de píxel en el interior even-odd. No se descarta un polígono por área algebraica (shoelace) cero: una figura autointersectada tipo bow-tie puede tener relleno válido aunque sus áreas firmadas se cancelen.

`path` acepta M/L/Q/C/Z en coordenadas de punto fijo 1/256 (enteros exactos con `|v| ≤ 268 435 456`; se rechazan `bool` y float), sin SVG, fuentes ni recursos externos. Gramática: 2–4096 comandos (el lector limita el documento a 20 000 nodos, así que 4096 sólo se alcanzan con paths casi enteramente de `M`/`L`), el primero `M`, sin subpaths vacíos y sólo `M` tras `Z`; un subpath abierto se cierra implícitamente. Las curvas se aplanan con aritmética entera (tolerancia 1/16 px, 1–64 segmentos por curva) y el path admite como mucho 65 536 segmentos incluido el cierre de cada subpath. El adaptador AggDraw (`moana.geometry.paths`, import perezoso) genera cobertura a escala nativa sobre la caja recortada al lienzo más 1 px de margen, aplica la regla **nonzero** y el umbral >=128 y devuelve una máscara binaria: «cobertura ≥128 ∩ caja de los puntos de control». Ese recorte es del path entero, así que un subpath lejano agranda la caja y puede cambiar píxeles de umbral cerca de otro. AGG engorda cada subpath ~1/4 px según su orientación, con picos de ~1 px en ángulos agudos, y la cobertura de subpaths superpuestos se acumula con su winding; un path de área nula no pinta y un path recortado puede variar en píxeles de umbral según el origen del buffer. Por eso la única garantía de píxel es estrecha: en un único subpath simple (sin autointersecciones ni agujeros), un píxel cuyo cuadrado está dentro del contorno pertenece a la máscara; no hay garantía de exclusión, y agujeros, paredes de 1 px, regiones de winding −1 y copias apiladas son resultado del backend (contraejemplos en ADR-023). Más de 2 097 152 celdas AGG por path es `BudgetExceeded` (`path_cells`), un límite del motor que no se eleva. Se etiqueta `aggdraw-v1`: reproducibilidad sólo con versiones/plataformas ensayadas (`TESTED_AGGDRAW_VERSIONS`); no se presenta como equivalente al backend entero, salvo en rectángulos de esquinas enteras, que coinciden con `rect`. Un backend ausente o no ensayado da `UNSUPPORTED_OPERATION`. No es necesario para completar el MVP (ADR-023). Flood fill utiliza cola iterativa acotada, nunca recursión Python.

Transformaciones pixel-perfect: traslación entera, espejo y rotaciones 0/90/180/270 alrededor del origen del grupo seguidas de traslación explícita. En coordenadas de índice, el giro horario de un punto respecto al origen es `(-y,x)`. Las cajas se transforman como conjuntos de píxeles, no redondeando esquinas geométricas. Escala entera de nearest-neighbor; rotación arbitraria queda fuera del perfil estricto.

## 7. Técnicas profesionales de Pixel Art

El flujo artístico comienza con brief (lectura, pose, focal point, material, luz, tamaño), thumbnail/silueta, clusters grandes, rampas, volúmenes, detalles y limpieza. La resolución objetivo manda la cantidad de detalle. Mantener familias de pendientes coherentes, transiciones deliberadas y espacio negativo legible; no aplicar blur, suavizado de imagen ni ruido genérico como «mejora».

Los presets artísticos son parámetros versionados y editables, no promesas de calidad. Su evaluación muestra imagen a 1× y 4×, paleta, silueta, mapa de clusters y alertas. El antialias manual interior puede usar colores de la rampa en píxeles elegidos explícitamente; nunca introduce cobertura fraccional oculta. Las excepciones de estilo (dientes, brillos aislados, píxeles sueltos) deben poder justificarse y silenciarse por región.

## 8. Siluetas, contornos y pixel clusters

Silueta = máscara de alfa>0 del resultado o región elegida. Componentes 4-conectados son el análisis predeterminado; 8-conectividad es una opción explícita para diagonales. Contorno exterior de ancho n: `dilate(mask,n)-mask`; interior: `mask-erode(mask,n)`, con vecindad Chebyshev 3×3 y repeticiones enteras. Las máscaras se calculan en coordenadas de lienzo, con exterior transparente. Selective outlining escoge colores desde una rampa y una máscara de luz declarada, conservando IDs de la operación.

Cluster = componente conectado de píxeles del mismo color (o del mismo índice de rampa si se solicita). El informe detecta componentes de 1 píxel, discontinuidades de borde y cambios abruptos de escalones en pendientes; esos hallazgos son advertencias artísticas, no fallos universales. La limpieza propone una operación editable; nunca borra automáticamente ojos o partículas. Las pruebas usan fixtures con diagonales, huecos, contactos de esquina y contornos pegados al límite.

Semántica implementada (MOANA-014, ADR-027): `moana.geometry.dilate`/`erode` aplican el cuadrado Chebyshev `2r + 1` (igual a `r` repeticiones de 3×3) con radio entero 1–16, recortan al lienzo antes de reservar y nunca envuelven; la erosión trata el exterior como transparente, de modo que una máscara pegada al borde conserva contorno interior en ese borde. `moana.techniques.outline_mask` es la definición literal anterior (`outer`/`inner`), y un hueco de la máscara recibe su propio contorno. La operación editable `outline` de §12 la pinta con un color de paleta. `moana.techniques.analyze_clusters` agrupa píxeles opacos del mismo RGBA con conectividad 4 (predeterminada) u 8 y emite advertencias `singleton` (componente de 1 px) e `irregular_steps` (escalera de 1 px de grosor, al menos 4 escalones, con dos escalones interiores consecutivos que difieren más de 1 px; una recta de Bresenham nunca avisa). Una `ClusterException(region_id, rules)` mueve a `suppressed` los hallazgos contenidos por completo en la región (como mucho 64 excepciones, que se comprueban con una cobertura de bits por píxel, de modo que el coste son los píxeles de los hallazgos); el análisis nunca modifica el documento ni la imagen. Clusters por índice de rampa, discontinuidades de borde y la operación de limpieza propuesta quedan para sus issues. Selective outlining implementado (MOANA-017, ADR-030): la operación `selective_outline` de §12 pinta el mismo anillo de `outline_mask` con un color base y, en cada tramo authored (máscara, orientación y `offset`), `ramp[band_index(...)]` con la luz de §9; los tramos se resuelven con la regla de `shade` (gana el último) y no hay una segunda regla de luz.

## 9. Paletas, color e iluminación

Una paleta tiene ID estable, colores con IDs únicos y valores `#RRGGBBAA` en mayúsculas. `#RRGGBB` no es formato canónico. Las operaciones referencian IDs de color, no copias del valor. Las rampas son listas ordenadas de IDs de sombra a luz; la luminancia creciente es una recomendación verificable, con excepción documentable para rampas estilizadas. La luminancia verificable es Y lineal entera: `2126·lin[R] + 7152·lin[G] + 722·lin[B]` con la tabla sRGB→lineal de 256 enteros escalada a 65 535 (ADR-014); un paso que no crece, un paso transparente o uno semitransparente produce advertencia, nunca rechazo. Cambiar un color modifica todos sus consumidores; duplicarlo permite una edición local independiente.

Perfil `strict`: alfa de colores {0,255}, capas con opacidad 255 y composición normal; el resultado usa sólo colores de la paleta más transparente. Perfil `rgba`: admite alfa 0–255 y composición, puede generar colores adicionales y lo declara en el reporte. No se cuantiza implícitamente. La exportación indexada rechaza exceso de colores salvo que el usuario pida un remapeo explícito y reciba su informe de error.

Luz artística: dirección discreta de ocho orientaciones o frontal, altura discreta 0–3, intensidad en pasos de rampa y luz ambiental en pasos. Las regiones/materiales referencian esa configuración. No se calculan normales 3D inexistentes: la profundidad/normal o las bandas de sombreado deben ser suministradas por máscaras o mapas validados. La política de hue shift pertenece a una rampa authored, evitando inventar colores mediante multiplicaciones RGB.

Semántica implementada (MOANA-015, ADR-028): la luz es `{direction, height, intensity, ambient}` con `direction` en `n`, `ne`, `e`, `se`, `s`, `sw`, `w`, `nw` (sentido horario desde arriba) o `front`, `height` 0–3 (0 rasante, 3 hacia el espectador; `front` no la usa) e `intensity`/`ambient` en pasos de rampa 0–4095. Cada banda declara una orientación authored (`facing`: una dirección de la luz o `none`); nada se infiere de los píxeles. La exposición es entera en −6..6: entre direcciones del plano a distancia angular `d` (pasos de 45°, 0–4), `(3 − height)·[2, 1, 0, −1, −2][d]`; un `facing` `front` recibe `2·height` (6 bajo una luz `front`); un `facing` del plano bajo una luz `front`, y `none` siempre, reciben 0. El índice de rampa de una banda es `clamp(ambient + round_half_away(intensity·exposición/6) + offset, 0, len(ramp) − 1)`, con mitades lejos de cero, así que orientaciones opuestas reciben niveles opuestos. Girar la luz cambia los tonos sin tocar ninguna máscara, y girar a la vez luz y orientaciones no cambia nada. `ramp_order: "monotonic"` emite como advertencias de render los hallazgos de luminancia de la rampa; `"stylized"` documenta la excepción estética y sólo conserva los de pasos transparentes o translúcidos.

## 10. Sombreado, dithering y materiales

Sombreado base: selección de índice de rampa mediante bandas de máscara con prioridades explícitas; en solapamientos gana la última banda listada. Clamp al rango de la rampa. Cada banda conserva ID y máscara editables. Pillow shading y luz contradictoria se señalan como revisiones humanas, sin clasificadores pretendidamente infalibles.

Semántica implementada (MOANA-015, ADR-028): la operación `shade` de §12 pinta, banda a banda y en orden, `ramp[índice]` (§9) sobre la parte visible de la máscara de cada banda: la máscara menos las de todas las bandas posteriores. Las partes son disjuntas y su unión es la de las bandas, de modo que en un solapamiento gana la última banda listada y un paso translúcido nunca se mezcla con otra banda; todos los colores pintados son colores de la rampa, porque sólo se elige un índice recortado y no se calcula, multiplica ni mezcla ningún color. Una banda vacía no pinta nada. Cada banda conserva su ID global y su `mask_id`: mover una sombra es editar la máscara de la banda, que cambia sólo los píxeles de la diferencia entre la máscara anterior y la nueva (sin nada encima). `moana.techniques` (`ShadeLight`, `exposure`, `band_level`, `band_index`, `last_wins`, `resolve_bands`) implementa la regla con enteros; el selective outlining de §8 y los materiales reutilizan esa luz, las orientaciones y `band_index` (ADR-030).

Dithering ordenado inicial: Bayer 2×2 `[[0,2],[3,1]]` o 4×4 `[[0,8,2,10],[12,4,14,6],[3,11,1,9],[15,7,13,5]]`. Parámetro entero `coverage` entre 0 y N²; escoger color B si threshold<coverage, A en caso contrario. Origen de patrón explícito `(ox,oy)` en lienzo; usar módulo matemático también en coordenadas negativas. Recortar por máscara antes de escribir. No cambiar fase entre tiles o frames salvo instrucción del autor.

Semántica implementada (MOANA-016, ADR-025): el umbral del píxel `(x, y)` es `M[(y−oy) mod N][(x−ox) mod N]` (fila desde `y`, columna desde `x`; `mod` con resultado en `[0, N)`), así que cada período `N × N` tiene exactamente `coverage` celdas B. La operación `dither` de §12 recorta por la máscara semántica `mask_id` (§11): las partes A y B son disjuntas, suman la máscara y ningún píxel exterior recibe pintura; un color transparente deja ver lo que había debajo. La fase sólo depende de las coordenadas de lienzo y de `origin`, de modo que trasladar `origin` por múltiplos de `N` no cambia nada y dos tiles contiguos con el mismo `origin` no tienen costura. `moana.techniques` (`OrderedDither`, `dither_mask`, `split_dither`) y `moana.geometry.select_periodic` implementan la regla con enteros, sin semilla, hash ni floats.

Materiales iniciales: piel, tela, metal, madera y piedra, definidos por rampa, bandas, densidad, escala y patrón; no por shaders arbitrarios. Textura aleatoria usa coordenadas y semilla según §14, nunca el RNG global. Cada preset incluye ejemplos propios, licencia/procedencia, rango de parámetros y pruebas de bordes, paleta, reproducibilidad y estabilidad temporal. Ruido y dithering se aplican a regiones elegidas; no a toda la imagen por defecto.

Semántica implementada (MOANA-017, ADR-030): cada preset es una fila inmutable `(name, version)` de `moana.core.materials.MATERIAL_PRESETS` con patrón, pasos de textura (`parts`), canales de hash, densidad y escala máximas, descripción, procedencia y licencia; una receta nueva añade una versión y nunca cambia una publicada. Versión 1: `skin` (`pores`, pasos −1/0, densidad ≤ 4, escala ≤ 2), `cloth` (`weave` en cesta, −1/0), `metal` (`streak`, 0/+1), `wood` (`grain`, −1/0) y `stone` (`speckle`, −1/0/+1, densidad ≤ 32); escala ≤ 4 salvo `skin`. El plano se divide en celdas `scale × scale` ancladas en `origin` (división entera hacia abajo); una celda candidata del patrón (`pores`/`speckle`: todas; `weave`: `cy mod 2 = 0` y `(cx div 2 + cy div 2) mod 2 = 0`, pares de celdas en filas alternas que se desplazan cada dos filas; `streak`: `(cx − cy) mod 4 = 0`; `grain`: `cy mod 3 = 0`) queda marcada si `cell_choice(seed, id_operación, cx, cy, 0, 64) < density` (§14) y desplaza todos sus píxeles un paso de rampa (−1, +1 en `streak`; en `speckle` el signo es `cell_choice(…, 1, 2)`). La operación `material` de §12 pinta cada píxel de la parte visible de cada banda (regla de `shade`) con `ramp[clamp(índice de la banda + paso de su celda)]`: ningún color fuera de la rampa, la misma semilla da la misma textura, otra operación no la cambia y la textura sigue a su `origin` entre fotogramas. Para mover un sprite texturizado sin que la textura «resbale», el mismo batch DEBE trasladar sus máscaras (`translate`) y desplazar el `origin` del material con `set_parameters` por el mismo `(dx, dy)`. No hay shaders, fórmulas ni código en el JSON. `moana.techniques` (`MaterialTexture`, `texture_step`, `texture_cells`, `texture_mask`, `split_texture`), `moana.core.procedural.cell_choices` y `moana.geometry.select_cells` implementan la regla con enteros.

## 11. Capas, máscaras y regiones

`layers` es una lista ordenada de abajo arriba. Una capa tiene ID global, nombre descriptivo, visible, locked, opacity, blend, opcional mask_id y operaciones ordenadas. Los grupos son nodos con lista de hijos, transform y opacidad; profundidad máxima 16. `locked` impide comandos de edición normales y no altera render. Grupos se componen en buffer aislado; la opacidad se aplica una vez al resultado del grupo.

Las máscaras son nodos con ID, geometría binaria y combinaciones union/intersect/subtract/xor; no pueden depender del render de una capa. Las referencias forman un DAG: se rechazan ciclos y referencias inexistentes antes de ejecutar. Región = ID semántico, mask_id y lista opcional de IDs de operaciones; permite «ojo izquierdo» sin inferir coordenadas desde el PNG. Los IDs no dependen del orden de arrays.

Semántica implementada (MOANA-013, ADR-022): las hojas de máscara reutilizan la geometría de las primitivas de §6, sin color y en coordenadas de lienzo. Las combinaciones pliegan de 2 a 64 IDs de máscara en orden: `union` (algún operando), `intersect` (todos), `subtract` (el primero y ninguno de los demás) y `xor` (un número impar de operandos). El resultado se recorta al lienzo, y una máscara vacía es válida. Se rechazan antes del render las referencias inexistentes o que no nombran una máscara (`unknown_mask`, `unknown_operation`), las repetidas (`duplicate_reference`), cada arista de un ciclo directo o indirecto (`mask_cycle`) y las cadenas de más de 16 máscaras (`too_deep`); como mucho hay 1024 máscaras y 1024 regiones. Una capa con `mask_id` se limpia fuera de su máscara antes de componerla, así que no modifica ningún píxel exterior. Norma para cuando existan grupos transformados (el schema 1.0 aún no los tiene): las máscaras no se moverán con la transformación de un grupo, sino que recortarán el contenido ya transformado.

Composición normal source-over sobre RGBA recto. Tras aplicar máscara y opacidad, `sa=round_half_up(alpha*opacity/255)`. Sea `D=sa*255+da*(255-sa)`: alfa final `round_half_up(D/255)`; canal final, si D>0, `round_half_up((sc*sa*255+dc*da*(255-sa))/D)`; si D=0, todo cero. `round_half_up(n/d)=(2*n+d)//(2*d)` para enteros no negativos. El resultado se normaliza por alfa cero. Primera versión sólo blend `normal`; multiply/screen serían extensión con contrato y fixtures propios.

## 12. Especificaciones JSON para agentes de IA

Documento UTF-8, objeto raíz, sin claves duplicadas, comentarios, NaN/Infinity ni coerciones. Los modelos Pydantic futuros usan `strict=True`, `extra='forbid'` y unions discriminadas. Validación de sintaxis se separa de referencias, capacidades y costes. Errores incluyen `code`, `json_pointer`, `message`, `context` sin datos sensibles; ordenados por pointer y código. Un documento puede ser estructuralmente válido y referirse a una capacidad aún no implementada: responder `UNSUPPORTED_OPERATION`, nunca ignorarla.

Campos raíz de v1: `schema_version` ("1.0"), `id`, `revision` (entero >=0), `seed` (0..2^64-1), `canvas`, `palette`, `layers`; opcionales `masks`, `regions`, `materials`, `animations`, `metadata`. Payloads de máscaras y regiones (MOANA-013, ADR-022):
- hoja: `{"id", "type": "pixel"|"line"|"rect"|"ellipse"|"polygon", ...parámetros de §6 sin color}`;
- combinación: `{"id", "type": "union"|"intersect"|"subtract"|"xor", "masks": [2–64 IDs]}`;
- región: `{"id", "mask_id", "operation_ids": []}`;
- capa: `mask_id` opcional;
- operación de dithering (MOANA-016, ADR-025): `{"id", "type": "dither", "size": 2|4, "coverage": 0..size², "origin": [ox, oy], "color_a", "color_b", "mask_id"}`, todos obligatorios;
- operación de contorno (MOANA-014, ADR-027): `{"id", "type": "outline", "mask_id", "width": 1..16, "side": "outer"|"inner", "color"}`, todos obligatorios;
- operación de sombreado por bandas (MOANA-015, ADR-028): `{"id", "type": "shade", "ramp", "ramp_order": "monotonic"|"stylized", "light": {"direction", "height": 0..3, "intensity": 0..4095, "ambient": 0..4095}, "bands": [1–64 × {"id", "mask_id", "facing", "offset": −4095..4095}]}`, todos obligatorios;
- operación de material (MOANA-017, ADR-030): `{"id", "type": "material", "preset": "skin"|"cloth"|"metal"|"wood"|"stone", "version": >=1, "ramp", "ramp_order", "light", "density": 0..64, "scale": 1..8, "origin": [ox, oy], "bands"}`, todos obligatorios; `version` debe existir para el preset (`unknown_preset_version`) y `density`/`scale` no pueden superar los máximos de su fila; `ramp_order`, `light` y `bands` como en `shade`;
- animación (MOANA-022, ADR-032): `{"id", "loop_count": 0..65535, "pivot": [x, y], "frames": [1–256 × {"id", "duration_ms": 1..60000, "overrides": [0–1024 × override]}]}`; `pivot` dentro del lienzo con bordes incluidos (`pivot_out_of_canvas`); override = `{"type": "set_visibility", "target_id", "visible"}` | `{"type": "translate", "target_id", "dx", "dy"}` | `{"type": "set_color", "target_id", "color"}` (forma de los comandos de §15, sin `base_revision`); `target_id` nombra una capa, operación o máscara (`unknown_target`) y `color` un color de la paleta (`unknown_color`); el tipo correcto del destino se comprueba al evaluar el frame;
- operación de contorno selectivo (MOANA-017, ADR-030): `{"id", "type": "selective_outline", "mask_id", "width": 1..16, "side": "outer"|"inner", "color", "ramp", "ramp_order", "light", "segments": [1–64 × banda]}`, todos obligatorios.

La colección raíz `materials` sigue aceptándose sólo vacía: la receta va embebida en la operación (nombre y versión); una biblioteca compartida de materiales queda para un issue posterior.

Ejemplos validados: `examples/specs/masked-eyes.moana.json` y `examples/specs/dither-dusk.moana.json` y `examples/specs/outlined-slime.moana.json` y `examples/specs/shaded-orb.moana.json` y `examples/specs/material-{skin,cloth,metal,wood,stone}.moana.json` y `examples/specs/bouncing-slime.moana.json` (animación de 4 frames). Defaults materializados en normalización: seed=0, revision=0, canvas.profile="strict", capas visible=true, locked=false, opacity=255, blend="normal", arrays opcionales vacíos. `metadata` sólo admite title, description, author, tags y provenance; strings <=4096 bytes, tags <=32. IDs `[a-z][a-z0-9_-]{0,63}`, únicos en todo el documento incluyendo colores, operaciones y frames. Los nombres humanos no sirven como claves.

Ejemplo mínimo normativo del primer hito (diseño, no ejecución disponible):

```json
{
  "schema_version": "1.0",
  "id": "sprite_demo",
  "revision": 0,
  "seed": 42,
  "canvas": {"width": 128, "height": 128, "profile": "strict"},
  "palette": {
    "id": "palette_main",
    "colors": [
      {"id": "ink", "rgba": "#182338FF"},
      {"id": "cloth", "rgba": "#36AFA5FF"}
    ],

  },

    {
      "id": "body",
      "name": "Cuerpo",
```

El JSON Schema se genera desde Pydantic (`moana.schema`, MOANA-002) y se versiona en `schemas/moana-document-1.0.schema.json`; no se mantiene un segundo validador de producto a mano. `examples/specs/minimal.moana.json` se valida con el modelo real. Precisiones de 1.0 (ADR-011): `revision` en 0..2^64-1; los miembros opcionales se omiten y `null` explícito se rechaza; `metadata` vacía equivale a ausente; rampa = `{id, colors}` con 2–4096 IDs de color distintos; el ID del documento y el de la paleta entran en la unicidad global; `name` de capa ≤4096 bytes; perfil `strict` exige alfa 00/FF, opacidad 255 y ≤256 colores. Un error que agrupa varios problemas los lista en `details`. La gramática de schema 1.0 corresponde al MVP implementado por MOANA-002 (primitivas estáticas, paleta y capas simples) y a sus ampliaciones compatibles de MOANA-013 (máscaras, regiones y `mask_id` de capa) y MOANA-007 (operación `path` y hoja de máscara `path` con `backend: "aggdraw-v1"` y `commands`, ADR-023) y MOANA-016 (operación `dither`, ADR-025) y MOANA-014 (operación `outline`, ADR-027) y MOANA-015 (operación `shade`, ADR-028). Esas ampliaciones no cambian la validez ni el digest de ningún documento anterior, y un lector anterior las rechaza explícitamente: con `UNSUPPORTED_OPERATION` las capacidades previstas (ADR-022, ADR-023) y con `VALIDATION_ERROR` (`union_tag_invalid`) `dither`, `outline` y `shade`, que no figuraban como previstas (ADR-025, ADR-027, ADR-028). En `shade`, una `ramp` inexistente es `REFERENCE_ERROR` `unknown_ramp`, el `mask_id` de una banda que no nombra una máscara es `unknown_mask` (`…/bands/i/mask_id`), los IDs de banda entran en la unicidad global (`duplicate_id`), los enteros son estrictos (`int_type`, `greater_than_equal`, `less_than_equal`), `direction`, `facing` y `ramp_order` fuera de su lista son `literal_error` y una lista de bandas vacía es `too_short` en `…/bands`. En `outline`, `width` es un entero estricto en 1–16 (`int_type`, `greater_than_equal`, `less_than_equal`), `side` fuera de `outer`/`inner` es `literal_error`, `color` inexistente es `unknown_color` y un `mask_id` que no nombra una máscara es `unknown_mask`. En `dither`, `size` y `coverage` son enteros estrictos (`bool` y float son `int_type`; un tamaño distinto de 2 o 4, `unsupported_size`; `coverage > size²`, `less_than_equal` en `…/coverage`), `color_a`/`color_b` inexistentes son `unknown_color` y un `mask_id` que no nombra una máscara es `unknown_mask`. Es una excepción previa a la primera publicación (no hay tags ni paquete publicado y esta especificación es `-draft`): 1.0 sigue abierta hasta la primera publicación; después, toda ampliación de gramática sube el minor. `materials` sólo se acepta vacía hasta definir su modelo; `animations` tiene gramática 1.0 desde MOANA-022 (ADR-032), con la misma excepción previa a la primera publicación (un lector anterior la rechaza no vacía con `UNSUPPORTED_OPERATION`). Payload de `path`: `{id, type: "path", backend: "aggdraw-v1", color, commands}` (la hoja de máscara omite `color`), con `commands` como arrays `["M", x, y]`, `["L", x, y]`, `["Q", cx, cy, x, y]`, `["C", c1x, c1y, c2x, c2y, x, y]` y `["Z"]` en unidades de 1/256 px; los errores de gramática son `VALIDATION_ERROR` con el pointer del comando. Grupos, materiales y animaciones requieren ampliar explícitamente el schema y documentar payloads junto al issue correspondiente, sin anunciar una gramática ejecutable que aún no existe. La extensión futura de operaciones exige registrar modelo, resolución, coste, raster, pruebas y documentación; no se admiten imports dinámicos desde JSON.

## 13. API pública de Python

Fachada v0.1 implementada en `moana.api` (MOANA-012, ADR-020; edición en MOANA-018, ADR-024):

```python
from moana.api import apply_edit, export_png, load_document, render, snapshot_digest

document = load_document("hero.moana.json")
result = render(document, frame_id=None, limits=None)
export_png(result, "hero.png", scale=1)
edited = apply_edit(
    document,
    {
        "schema_version": "1.0",
        "base_revision": document.revision,
        "base_snapshot": snapshot_digest(document),
        "commands": [{"type": "set_color", "target_id": "body_fill", "color": "ink"}],
    },
)
assert edited.revision == document.revision + 1
```

- `load_document(source: str | os.PathLike[str] | bytes | Mapping[str, object], *, limits: ParseLimits = DEFAULT_PARSE_LIMITS) -> Document` valida y normaliza. Un path es de confianza porque lo pasa la API, nunca porque lo nombre un documento. Un `str` que empieza por `{` o `[` se rechaza (`ValidationError`, `json_text`): el JSON entra como bytes o mapping. El archivo debe ser regular; se abre sin bloquear y se leen como mucho `max_bytes + 1` bytes. Un fallo de lectura es `ReadError` (`READ_ERROR`, salida 5) con `reason`, `file_name` (≤255 caracteres) y `errno`, sin ruta completa.
- `render(Document, *, frame_id: str | None = None, limits: RenderLimits | None = None, deadline: Deadline | None = None) -> RenderResult` delega en `moana.render.render` (MOANA-010, ADR-018); con `frame_id` delega en `moana.animation.render_frame`, que evalúa todos los frames de su animación contra la base y renderiza ese frame con `frame_id` en la procedencia (MOANA-022, ADR-032; `moana.render.render` sólo dibuja la base: un frame del documento es `ReferenceError` `frame_not_evaluated`); no escribe archivos ni modifica el documento. `RenderResult` contiene width, height, RGBA inmutable (`bytes`), digest, warnings, renderer_version y provenance; `provenance` incluye siempre `vector_backend` y `vector_backend_versions`: con paths, `aggdraw-v1` y (`aggdraw==…`, `pillow==…`); sin ellos, `null` y `[]`.
- `export_png(RenderResult, path, *, scale: int = 1, overwrite: bool = False, limits: RenderLimits | None = None) -> ExportManifest` escribe un PNG RGBA de forma atómica mediante `moana.export.export_png` (MOANA-011, ADR-019), que acepta además `mode` (`rgba`/`indexed`) y `palette`.
- `inspect_document(Document, *, limits=None) -> DocumentReport` resume identidad, lienzo, paleta, capas (con `mask_id`), máscaras, regiones y presupuesto estimado; un exceso se informa (`within_limits`, `exceeded`), no se lanza. `capabilities() -> Capabilities` separa lo disponible de lo previsto (incluye `collections`, `mask_types`, `planned_mask_types` y `backends`: `BackendSummary` con nombre, disponibilidad, versión de AggDraw y de Pillow, motivo y versiones ensayadas). Sin backend de paths utilizable, `path` aparece como previsto, nunca desaparece; es una capacidad de ejecución: el schema acepta `path` igualmente y sólo `render` lo rechaza (ADR-023). `dither` figura siempre como disponible e `inspect_document` resume esa operación con su color A en `color`; su `BudgetReport` separa `operations` (del documento) de `fills` (rasterizados, el valor que compara `max_operations`) (ADR-025). `moana.schema` exporta la tabla de miembros por tipo `OPERATION_MEMBERS`/`MASK_MEMBERS` (`NodeMembers(colors, masks, geometry)`, de sólo lectura): qué miembros de cada `type` guardan colores de paleta, referencias a máscaras y geometría (`dither`: `color_a`/`color_b`, `mask_id`, sin geometría; `origin` no es geometría; `outline`: `color`, `mask_id`, sin geometría, así que `set_color` lo recolorea y `set_geometry`/`translate` responden `not_geometric`; `shade` (ADR-028): sin color, `ramps=("ramp",)` e `items=(("bands", fila con `mask_id`),)`, columnas opcionales para rampas y arrays de objetos con ID propio, así que `set_color` responde `multiple_colors`, las bandas no son objetivo de ningún comando y borrar su máscara o su rampa es `live_reference`). Validación, referencias, inspección y edición la recorren en lugar de comprobar clases (ADR-025). `outline` figura siempre como disponible (ADR-027). `shade` figura siempre como disponible e `inspect_document` lo resume con `color: null` (ADR-028).
- `analyze_clusters(Document, *, connectivity=4, exceptions=(), limits=None, deadline=None) -> ClusterReport` comprueba primero la configuración (conectividad, regiones repetidas, como mucho 64 excepciones: `too_many_exceptions`). Después, con `moana.render.render_with_regions`, valida el documento una vez, resuelve las regiones (`ReferenceError` `unknown_region`, antes de renderizar) y admite toda la solicitud contra un solo presupuesto: render, máscaras de región leídas una a una, cobertura de regiones (8 bytes por píxel) y análisis (`cluster_bytes`: 512 bytes por run opaco como máximo). Devuelve clusters, `warnings` y `suppressed` (§8, §19) en orden determinista. Más de 262 144 runs opacos es `BudgetExceeded` `cluster_runs`, y el `deadline` se respeta en cada etapa. No modifica el documento ni su digest. No tiene comando CLI (ADR-027).
- `resolve_region(Document, region_id) -> ResolvedRegion` resuelve una región por ID: su máscara, las máscaras de las que depende (operandos primero), sus operaciones y las capas que las contienen. Un ID desconocido es `ReferenceError` (MOANA-013, ADR-022; reexportada desde `moana.schema`).
- La identidad de snapshot es `moana.schema.snapshot_digest(document)`, reexportada en `moana.api`. Todos los retornos son congelados y sin objetos NumPy ni Pillow.
- `apply_edit(Document, EditBatch | path | bytes | mapping, *, limits=DEFAULT_PARSE_LIMITS) -> Document` devuelve el documento de la revisión siguiente (§15, ADR-024); `edit_document(...)` devuelve además `EditResult` (snapshot nuevo e IDs afectados) y `load_edit_batch(source)` lee y valida un batch con la misma lectura acotada que `load_document`. `capabilities()` lista el catálogo en `edit_commands`; `PLANNED_FUNCTIONS` está vacío.

Errores públicos (`moana.core.errors`): `MoanaError` y subclases `ValidationError` (con `OutOfBoundsError` para acceso a píxel fuera del lienzo), `ReferenceError`, `BudgetExceeded`, `UnsupportedVersion`, `UnsupportedOperation`, `EditConflict`, `ExportError` y `ReadError`. Cada clase declara `code` estable y el código de salida de la CLI (ADR-010, ampliado por ADR-020 con `READ_ERROR` = 5).

CLI `moana` (también `python -m moana.cli`):

- Comandos: `validate DOC`, `inspect DOC`, `render DOC` (en memoria, sin escribir), `export DOC OUT.png [--scale 1..64] [--overwrite]`, `edit DOC BATCH` y `capabilities`. Opciones `--version` y `--debug` (antes o después del comando), sin abreviaturas.
- `edit DOC BATCH` aplica el batch JSON de §15 e imprime en una sola línea un objeto JSON con `edit` = `revision`, `base_revision`, `base_snapshot`, `snapshot_digest`, `affected_ids`, `document_id` y el documento normalizado completo (`document`); no escribe ningún archivo (persistir es de `project`, MOANA-020). Un conflicto sale con 4.
- Cada invocación escribe un único objeto JSON en una línea de stdout (`ok`, `command` y el resultado, o `error {code, exit_code, message, json_pointer, context, details}`) y, si falla, una línea breve en stderr. Un error de uso es `VALIDATION_ERROR` (`reason: usage`) con mensaje fijo.
- Códigos: 0 éxito, 2 entrada inválida o capacidad no disponible, 3 presupuesto, 4 conflicto, 5 I/O (lectura, exportación o stdout cerrado), 1 fallo interno y 130 interrupción (objeto `INTERRUPTED`). No se muestran tracebacks salvo con `--debug`.

## 14. Renderizado y determinismo

Mismo documento normalizado + versión de renderer + lock + parámetros produce los mismos bytes RGBA. El perfil entero debe producir igualdad RGBA entre OS soportados y distintas semillas de hash de Python. Un documento con paths (`aggdraw-v1`, ADR-023) tiene garantía limitada: igualdad entre procesos y semillas de hash en la misma plataforma y versión ensayada de AggDraw; entre plataformas sólo se garantizan los oráculos documentados (contención de un subpath simple, simetría, regla nonzero y rectángulos enteros iguales a `rect`), y sus casos no se mezclan con el corpus entero de determinismo. Evidencia entre plataformas: local macOS; matriz pendiente en `main`. Orden de capas/operaciones viene de arrays; no se usa orden de sets, concurrencia, locale, reloj ni hash() como semilla. Los paths de archivos y timestamps no forman parte de la identidad visual.

Normalización canónica: materializar defaults, ordenar claves de objetos, preservar arrays, JSON UTF-8 sin espacios, ensure_ascii=false, sin floats. Color canónico mayúsculo. Digest visual = SHA-256 de width y height como uint32 big-endian concatenados con RGBA row-major. Digest del documento incluye toda la representación canónica; la clave de caché agrega versión de renderer, backend, lock digest y frame. La revisión cambia el documento aunque la imagen no cambie.

Aleatoriedad procedural por celda: SHA-256 de la codificación JSON canónica del array `[seed, operation_id, x, y, channel, algorithm_version]`; obtener u como primeros 8 bytes big-endian; mapear a rango n con `u*n//2^64`. No es criptografía del producto; es una secuencia determinista cuyo algoritmo se versiona. Añadir una operación no cambia la textura de otra. Frame sólo entra en la semilla cuando el efecto declara variación temporal.

Cachés son optimización: activadas/desactivadas deben dar igualdad exacta. No hay procesamiento paralelo hasta demostrar orden y memoria acotados. PNG/GIF pueden diferir en bytes comprimidos entre versiones; la garantía base compara píxeles decodificados y metadata semántica. Igualdad byte a byte de un export sólo se garantiza en un entorno de codec fijado, sin metadata volátil.

## 15. Edición no destructiva

El documento es el artefacto editable primario; el PNG es derivado. Un batch contiene `schema_version`, `base_revision`, `base_snapshot` y comandos tipados. `base_snapshot` es `sha256:` seguido del digest hexadecimal del documento normalizado de origen (§14), calculado por `moana.schema.snapshot_digest(document)` (reexportado en `moana.api`); el digest no se serializa dentro del propio documento. Se verifican ambas precondiciones para distinguir ramas con el mismo número de revisión. Catálogo inicial: `set_color(target_id,color)`, `set_geometry(target_id,geometry)`, `translate(target_id,dx,dy)`, `set_visibility(target_id,visible)`, `replace_palette_color(target_id,rgba)`, `insert_operation(layer_id,after_id|null,operation)`, `remove(target_id)`, `reorder(target_id,after_id|null)` y, desde MOANA-017 (ADR-030), `set_parameters(target_id,parameters)`. `after_id=null` inserta al principio del contenedor. Sólo se reordena dentro del mismo contenedor; traslado entre capas será comando explícito posterior.

Una revisión o un digest de snapshot que no coincide con el documento actual produce EditConflict. Validar todos los comandos y la escena resultante antes de aceptar; un fallo revierte todo. No se admiten cambios directos de id, schema_version ni revision. Rechazar borrado con referencias vivas, edición de capa bloqueada y comandos ambiguos. Batch exitoso incrementa revision exactamente en 1, incluso si el resultado visual no cambia. Se preservan IDs existentes, bytes fuente de assets y orden de nodos no afectados.

Historial: snapshots inmutables identificados por digest, con batch canónico, digest del padre y revisión numérica local a la rama; undo/redo selecciona estados existentes, mientras un nuevo edit sobre estado anterior crea rama lógica y descarta sólo el cursor redo activo, no los archivos guardados. Un cambio local puede modificar sombra/contorno dependiente; el manifiesto indica IDs afectados y bbox de diferencia, evitando prometer que ninguna dependencia cambia. Se informa el diff antes/después y se conserva el archivo anterior al guardar con sobreescritura explícita.

Semántica implementada (MOANA-018, ADR-024; `moana.editing`): el batch es estricto (`extra` prohibido, 1–1024 comandos, `after_id` obligatorio con `null` explícito) y se lee con los mismos límites que un documento. Lo que el editor sabe de cada tipo de operación o máscara sale de la tabla de miembros `OPERATION_MEMBERS`/`MASK_MEMBERS` de `moana.schema` (ADR-025); un `dither` (dos colores, una máscara, sin geometría) se puede borrar, reordenar e insertar, pero no recolorear con `set_color` ni desplazar. Objetivos: `set_color` sobre operaciones con exactamente un miembro de color (otro número: `multiple_colors`); `set_geometry`/`translate` sobre operaciones y hojas de máscara (una máscara combinada no tiene geometría: `not_geometric`); `geometry` contiene exactamente los miembros geométricos del tipo (`at`; `start`/`end`; `box`; `points`; `commands`) y `translate` mueve píxeles enteros (un path, `256·d` unidades; una coordenada fuera de rango da `out_of_range` en `/commands/i` con `member`); `set_visibility` sobre capas; `replace_palette_color` sobre colores, también si los usan capas bloqueadas (cambia la paleta, no la capa); `insert_operation` en una capa tras una operación de esa capa, con un ID nuevo en todo el documento y en el batch (`duplicate_id`) y distinto de los eliminados en el mismo batch (`reused_id`); `remove` sobre operaciones, capas (con sus operaciones), máscaras, regiones, colores y rampas; `reorder` sobre cualquier nodo de una lista, dentro de ella. Un ID inexistente es `ReferenceError` (`unknown_target`), uno de otra clase `ValidationError` (`invalid_target`), una capa bloqueada `locked_layer` y un borrado con referencias vivas `ReferenceError` (`live_reference`, un detalle por referencia). Revisión distinta de la actual (menor o mayor): `EditConflict` `stale_revision`; misma revisión con otro digest: `snapshot_mismatch`; revisión actual ya máxima: `revision_overflow` antes de aplicar ningún comando. Los comandos se aplican en orden sobre una copia normalizada; el resultado se revalida completo (`invalid_result` si falla) y el documento fuente nunca cambia. Las bandas de un `shade` (ADR-028) son items con ID global: ningún comando las acepta como objetivo, un `insert_operation` comprueba también sus IDs (`duplicate_id`/`reused_id` en `/commands/i/operation/bands/k/id`) y un `shade` borrado, o su capa, retira los IDs de sus bandas; las bandas de un `material` y los tramos de un `selective_outline` siguen la misma regla. `set_parameters` (ADR-030; `{type, target_id, parameters}`) sustituye en una operación desbloqueada sólo los miembros de valor de la columna `parameters` de su fila (`shade`: `light`, `ramp_order`; `material`: además `density`, `scale`, `origin`; `selective_outline`: `light`, `ramp_order`, `width`, `side`), revalidando el payload combinado; otra clave es `not_parameter`, un objeto vacío `empty_parameters` y un tipo sin parámetros `no_parameters`. IDs, referencias, items y geometría no cambian. El resultado lista sólo los IDs afectados directamente (objetivos, insertados y eliminados, con las bandas de una operación insertada o eliminada tras el ID de la operación); el bbox de diferencia y los consumidores indirectos se calcularán con el manifiesto del historial de `project` (MOANA-020). No hay comandos de bloqueo, de traslado entre contenedores ni JSON Patch.

Historial implementado en memoria (MOANA-019, ADR-026; `moana.editing.History`, sin persistencia en disco ni en la fachada): valor congelado creado con `History.start(document, *, limits)`; cada operación devuelve un `History` nuevo. Cada `Snapshot` se indexa por `snapshot_digest` y guarda el `Document` exacto, el digest del padre, el JSON canónico del batch que lo produjo (claves ordenadas, sin espacios, `null` explícito), sus `affected_ids` y su revisión, local a la rama y nunca clave. Un cursor separado selecciona el estado: `undo` (al padre; en la raíz `ValidationError` `no_parent`), `redo` (al hijo redo activo; sin él `no_redo`) y `checkout(digest)` (digest desconocido: `ReferenceError` `unknown_snapshot`) sólo mueven el cursor y devuelven el mismo objeto guardado, sin operaciones inversas. Sólo `edit(batch)` añade un snapshot, aplicando `apply_batch` al documento del cursor (su base debe ser la del cursor; un fallo no añade nada). El snapshot nuevo pasa a ser el redo activo del cursor: editar tras un undo crea una rama y sólo invalida ese redo; los estados anteriores siguen accesibles por digest (`children_of`, `leaves`). Un resultado cuyo digest ya existe se reutiliza si su padre es el cursor (conserva el batch y los IDs afectados del primero). Bajo otro padre es `EditConflict` (`existing_snapshot`, reintentable con `checkout`): el historial es un árbol. Tras un edit no hay redo activo. El constructor valida un historial construido a mano (`invalid_history`). Presupuesto: `HistoryLimits`, que sólo se puede bajar. Admite como mucho `MAX_HISTORY_SNAPSHOTS` = 1024 snapshots, raíz incluida, y `MAX_HISTORY_BYTES` = 32 MiB de JSON canónico de documentos y batches. Esa medida es determinista y proporcional, pero no es una cota de RAM: se observó un factor de unas 10–17× (≈0,3–0,5 GiB al máximo), y con documentos de 8 MiB caben 4 versiones. Superar el presupuesto es `BudgetExceeded` (`history_snapshots` o `history_bytes`) antes de añadir; no hay desalojo.

## 16. Formato de proyectos

Formato base `.moana.json` autocontenido para geometría. Proyecto con assets: directorio con `project.moana.json`, `assets/`, `history/` opcional y `previews/` derivado. `project.moana.json` es un sobre ProjectManifest separado de Document: `{kind: "moana-project", project_version: "1.0", document: Document, assets: [AssetRef], history: []}`. `history` es opcional y vacío por defecto; el resto de campos es obligatorio. El lector distingue el sobre por `kind` y aplica su modelo propio con extra=forbid; no agrega `assets` como campo desconocido de Document. Cada AssetRef declara id, path POSIX relativa, mime, byte_length y sha256; los IDs de assets son únicos en el sobre y no colisionan con IDs del documento. Únicos assets iniciales: PNG RGBA decodificado; no Python, pickle, fuentes, SVG externo ni URL. `save_project` escribe a temporal hermano, fsync cuando sea viable y reemplaza atómicamente; los assets se verifican antes del commit del manifiesto. Assets y snapshots se guardan bajo rutas inmutables derivadas del hash; actualizar el proyecto nunca reemplaza sus bytes antes del commit del nuevo manifiesto. Los assets sobrantes tras un fallo son huérfanos recuperables, no corrupción del proyecto previo; su recolección es una acción explícita posterior.

Contenedor `.moana` ZIP opcional usa esas mismas rutas; se inspecciona antes de extracción: no rutas absolutas, `..`, symlinks, duplicados, nombres normalizados en colisión ni ratios de expansión excesivos. Máximo 256 entradas, 64 MiB comprimidos, 256 MiB descomprimidos, ratio 100:1 por entrada y total. Prohibir resolver enlaces fuera de la raíz. Los perfiles en memoria conservan límites aunque no se use ZIP.

Implementado (MOANA-020, ADR-029; `moana.project`, sin fachada ni CLI): `Project(document, assets, history)` congelado; `save_project` (directorio), `save_project_archive` (`.moana` ZIP determinista), `save_document` (`.moana.json` canónico) y `load_project` (directorio, ZIP o JSON; un JSON con `kind` es un sobre, sin él un documento) con `ProjectLimits`, que sólo se pueden bajar. Disposición: `assets/<sha256>.png`, `history/snapshots/<hex del snapshot_digest>.json` (JSON canónico del documento) e `history/batches/<sha256>.json` (batch canónico); `AssetRef.path` debe ser exactamente `assets/<sha256>.png` y `mime` `image/png`. `history` lista `{snapshot, parent, batch, redo}` en orden de inserción (padre antes que hijo, `redo` = hijo redo activo); el cursor es el documento del sobre. Guardar comprueba antes el presupuesto de carga, escribe y sincroniza los archivos de contenido que faltan (los existentes con los mismos bytes se reutilizan, nunca se reescriben) y confirma el manifiesto al final (`os.link` sin sobrescritura; `os.replace` con `overwrite=True`); un fallo de escritura es `ExportError` con `reason`, nombre relativo y `errno`, y deja intacto el proyecto anterior. Cargar lee todo en memoria y verifica antes de devolver: el sobre (≤ 9 MiB, profundidad 34, 32 768 nodos, sin claves duplicadas; `invalid_manifest`, documento con punteros bajo `/document`), cada asset (≤ 128 assets, ≤ 32 MiB cada uno, longitud y SHA-256 exactos: `checksum_mismatch`; PNG RGBA de 8 bits con `IHDR` comprobado antes de Pillow, ≤ 2048 por eje y ≤ 16 777 216 píxeles en total; APNG, perfil ICC o datos corruptos se rechazan) y cada entrada del historial (hash, documento y batch canónicos, y `apply_batch` del padre reproduce el digest; si no, `invalid_history`), reconstruido con el constructor validado de `History`. La convergencia sigue rechazada (ADR-026 §4). Guardar comprueba también que el JSON canónico del documento, de cada snapshot, de cada batch y del manifiesto cabe en los límites de lectura (`BudgetExceeded` antes de escribir). Rutas confinadas: la del llamador sigue enlaces; las internas nunca (descriptores de directorio en POSIX, comprobación previa en Windows), sólo archivos regulares y `límite + 1` bytes (`ReadError`). El ZIP nunca se extrae a disco; su inspección (`unsafe_archive` con `entry_reason`: `absolute_path`, `parent_reference`, `invalid_name`, `symlink`, `duplicate_name`, `name_collision` tras NFC + casefold, `expansion_ratio`, `encrypted`, `compression`, `unexpected_entry`; o `corrupt_archive`, o `BudgetExceeded` `archive_*`) ocurre antes de descomprimir. Un ZIP admite 128 snapshots de historial (256 entradas). Sus bytes son deterministas para una misma zlib pero dependen de ella; la identidad estable entre plataformas es el hash del manifiesto. `previews/` y la recolección de huérfanos quedan pendientes.

Separar schema_version de versión del paquete y renderer. Minor de schema sólo añade campos con defaults compatibles. 1.0 sigue abierta hasta la primera publicación; después, toda ampliación de gramática sube el minor. Ampliar 1.0 antes de esa publicación (máscaras y regiones, ADR-022) es la única excepción y no exige migración; el lector estricto soporta versiones explícitas, no «tolera» versiones nuevas. Migraciones son funciones puras probadas por fixture, preservan copia original y registran versión de origen; no migrar destructivamente al abrir. Guardar/cargar debe preservar semántica, IDs y resultado.

Implementado (MOANA-021, ADR-031): sólo `schema_version` y `project_version` (`MAJOR.MINOR`) son versiones de formato; la versión del paquete, `RENDERER_VERSION` y la del estimador nunca seleccionan una migración. `moana.schema.MigrationRegistry(member, current, migrations)` es un registro inmutable de pasos `Migration(id, source, target, apply)` comprobado al construirse (origen < destino ≤ actual, un paso por origen, cadenas de ≤ 16 pasos que llegan a la actual). Los registros de producción `DOCUMENT_MIGRATIONS` y `PROJECT_MIGRATIONS` conocen sólo 1.0 y no registran ninguna migración: 1.0 es la única versión que ha existido, y los formatos 0.8/0.9 de las pruebas son de prueba (`tests/fixtures/migration`, miembro `test_only_format`), nunca publicados. Leer no migra: otra versión es `UnsupportedVersion` con `field` y `relation` (`future`, `past`, `unknown`) o, si hay cadena registrada, `migration_required`; un `project_version` textual distinto de 1.0 es `UnsupportedVersion` en `/project_version` y la versión del documento de un sobre se informa en `/document/schema_version`. `migrate_document(tree, *, registry, limits)` es puro (sin E/S; hojas JSON obligatorias, `invalid_value`; copia acotada antes y después de cada paso; cualquier excepción de un paso que no sea `MoanaError`, o una salida no JSON, cíclica o fuera de límites, es `migration_failed` con el ID del paso, sin encadenar ni citar datos; resultado validado; un documento actual es la identidad). Los batches de edición conservan su contrato de versión. `moana.project.migrate_project(source, destination, *, registry, limits)` lee la fuente como `load_project` sin escribirla, migra en memoria, conserva los assets y guarda un proyecto nuevo sin sobrescritura (`exists`; un destino igual a un directorio fuente o dentro de él es `destination_inside_source`); el sobre registra `migrations` (`MigrationRecord`: tipo de origen, miembro migrado, versiones de origen < destino, 1–16 pasos y la copia exacta del JSON original en `migrations/<sha256>.json`, única por registro y verificada al cargar; omitido si está vacío; ≤ 8 registros y cada copia ≤ 9 MiB). Una fuente actual no escribe nada; una fuente antigua con historial es `history_not_migratable`. Un fallo en cualquier paso deja el original intacto y ningún manifiesto en el destino.

## 17. Animaciones y spritesheets

Animación tiene ID, frames ordenados, loop_count (0 infinito), canvas y paleta compartidos. Un frame tiene ID, duration_ms entero 1–60 000 y una lista de overrides tipados sobre IDs base; cada frame se evalúa sobre el documento base, nunca sobre el resultado del anterior. Los overrides no contienen base_revision ni cambian la revisión persistente. MVP de animación: visibilidad, geometría y color; sin tween implícito. Un pivote entero común evita jitter; los desplazamientos artísticos son explícitos. Máximo 256 frames y 16 777 216 píxeles de frame acumulados por export.

Implementado en MOANA-022 (ADR-032), sin CLI ni exportación: `moana.animation` evalúa cada frame como la base estática (sin `animations`) más sus overrides, con las reglas del editor (`moana.editing.apply_commands`: tipo de destino, capas bloqueadas, rangos y revalidación) y sin revisión nueva; `evaluate_frame`/`evaluate_animation` devuelven `FrameEvaluation` (índice, `start_ms`, `duration_ms`, `pivot`, documento). `render_animation(document, animation_id, *, frame_ids=None, limits, parse_limits, deadline)` y `render_frame` trabajan en dos pasadas con un solo documento de frame a la vez: evalúan todos los frames de la animación antes de dibujar (un override inválido rechaza toda la solicitud), estiman los pedidos con `moana.render.plan_frame` y los admiten con `moana.render.admit_sequence` contra un único presupuesto (Σ visitas, Σ píxeles de frame y el mayor pico de trabajo más el RGBA y `RESULT_OVERHEAD_BYTES` de cada resultado retenido); después reevalúan y renderizan cada frame pedido con `moana.render.render_admitted`. Cada frame se renderiza una vez en el orden pedido; `loop_count` es dato de reproducción. El frame no entra en la semilla: texturas de material y fases de dithering quedan ancladas a su `origin` en todos los frames, así que mover un sprite texturizado (material/dither) en un frame desliza la textura respecto del sprite: en el MVP no hay override de `origin`; la textura queda anclada a su origin. Validar N frames cuesta CPU que no cuenta en `pixel_visits`: los anfitriones deben pasar un `Deadline`. Límites en `moana.core.limits`: 64 animaciones, 256 frames, 1–60 000 ms, 1024 overrides por frame, `loop_count` ≤ 65 535.

Spritesheet inicial: grid uniforme en orden de frames, columnas declaradas, padding>=0, margin>=0; cada frame mantiene canvas sin trim por defecto. Manifest JSON versionado incluye frame_id, rect `[x,y,w,h]`, duration_ms, pivot, source_size, trim_offset y digest. Packing compacto será opcional con tie-break por frame_id y nunca rotará sprites implícitamente. Exportar spritesheet y recortar según manifest reconstruye exactamente cada frame.

Se revisan siluetas, volumen, paleta, contacto con suelo y fase de dithering a lo largo de la secuencia. Un onion skin es sólo preview, no altera salida. Tests cubren loop, frame único, overrides inválidos, duraciones máximas, overflow de sheet y reconstrucción de atlas.

## 18. Exportación PNG, GIF y formatos adicionales

PNG RGBA es formato maestro: transparente normalizado, escala entera opcional, compresión fijada y metadata de procedencia separada o estable. PNG indexado usa orden declarado de paleta y transparencia explícita, <=256 entradas; sin cuantización silenciosa. PNG conserva píxeles al decodificarse.

GIF admite paleta compartida <=256, alfa binario y transparencia reservada; si hay alfa intermedio exigir background de aplanado o rechazar. Duración debe ser múltiplo de 10 ms; por defecto rechazar pérdidas, con modo de redondeo explícito que devuelve duraciones efectivas. Exportar frames completos con disposal configurado, comprobar composición decodificada y preservación de tiempo; duplicados que el encoder fusione se verifican por timeline equivalente. Reservar el índice transparente reduce a 255 colores opacos.

WebP lossless y APNG son entregas posteriores, condicionadas a capacidad real del build de Pillow y pruebas roundtrip. Si un encoder no existe, UnsupportedOperation; no fallback oculto. Atlas PNG+JSON es el intercambio adicional prioritario. La creación de archivos es atómica y por defecto no sobrescribe. `overwrite=False` requiere un commit sin reemplazo atómico en el filesystem de destino; un exists() seguido de replace() no es suficiente por la carrera entre procesos. Si esa garantía no está disponible, fallar explícitamente; con overwrite=True puede usarse reemplazo atómico de temporal hermano. Cada export devuelve path, media_type, dimensiones, frames, hashes y advertencias. No se confunde un preview escalado con el sprite maestro.

## 19. Control de calidad gráfico

Hard checks: dimensiones correctas, alfa normalizado, paleta estricta, referencias válidas, ausencia de píxeles fuera de máscara y reproducibilidad. Soft checks: clusters aislados, bordes accidentados, contraste entre partes, lectura de silueta, exceso de colores, ruido, coherencia de luz y estabilidad temporal. No convertir heurísticas artísticas en rechazos silenciosos.

Cada incidencia contiene rule_id, severity, bbox, region_id opcional, explicación y evidencia; orden estable por regla, región, y,x. Parámetros y supresiones por región quedan en configuración de evaluación, no modifican la imagen (implementado para clusters en MOANA-014: `ClusterFinding` y `ClusterException`, ADR-027). Métricas numéricas: colores distintos, área opaca, componentes, proporción de singletons, bbox, diferencia por frame y porcentaje de píxeles cambiados.

Rúbrica humana: legibilidad a 1×, silueta, clusters, paleta, luz/material y continuidad temporal; escala 1–5 con justificación. Objetivo para ejemplos de referencia: >=4 por categoría relevante y ningún hard check fallido, evaluado por una persona y documentado; no se atribuye una aprobación humana a un agente. El primer corpus incluye personaje, criatura, objeto, tile y ciclo animado, con fuente editable y derechos claros.

## 20. Seguridad y validación

Documentos son datos, nunca código: prohibidos eval/exec, pickle, import dinámico, shell, acceso de red y paths libres en operaciones. Parsing JSON limita bytes antes de cargar (8 MiB), profundidad (32), número total de nodos (20 000), operaciones (10 000), capas/grupos (128), vértices por operación (4096) y colores (256 strict; 4096 rgba). Validar dimensiones y productos antes de crear arrays. Fallar en la fase de presupuesto, no después de una asignación enorme.

Presupuesto por solicitud predeterminado: 256 MiB de buffers estimados incluyendo temporales/cache, 100 000 000 visitas estimadas de píxel y 16 777 216 píxeles acumulados de frames. Coste de operación = bbox recortada × pasadas, salvo líneas/paths, cuyo coste incluye segmentos/pasos antes del clipping; flood fill <=área, morfología incluye vecindad y radio. El límite de op count no sustituye el límite de trabajo. El estimador implementado (`budget-v8`; ADR-012, ADR-018, ADR-022, ADR-023, ADR-025, ADR-027, ADR-028 y ADR-030: visitas = raster + una pasada de pintado sobre la caja recortada) suma también limpieza, composición y copia de cada frame, el acumulador de composición y la mayor máscara temporal. Para cada capa visible con máscara añade la expresión expandida sin memo (el compositor reevalúa un nodo compartido en cada referencia, y el coste lo cuenta así): cada nodo evaluado cuesta al menos 1 visita, también si está vacío, de modo que un DAG de máscaras vacías nunca sale gratis; un nodo cuya caja de resultado es vacía cuesta sólo ese suelo, porque no se evalúan sus operandos ni se rasteriza la hoja. Una hoja no vacía suma su raster y una combinación no vacía `2×` su caja más, por operando, su coste y un plegado sobre su caja; copiar los bits del resultado suma su caja, y limpiar fuera de la máscara, `A`. En bytes suma el pico de evaluación más una copia del resultado. `composition_cost` aplica el mismo suelo y las mismas fórmulas sin el raster de las hojas, así que lo que admite `plan_budget` lo compone `render`. Sin máscaras, el resultado es idéntico a `budget-v2`. Cada path (`budget-v4`) cuesta, sin importar AggDraw, `S + celdas + 3·área(B')` visitas (sólo `S` si su caja recortada es vacía), con `S` segmentos aplanados, `B'` la caja recortada más 1 px de margen y celdas acotadas por `min(2L + 3S, 3S·(W'+H'+1))` (`L` = longitud Manhattan del polígono de control en píxeles); en bytes, `área(B) + 2·área(B') + 24·celdas + 256·comandos + 128 KiB` (memoria nativa fija de AGG, que `tracemalloc` no ve). Si las celdas superan 2 097 152 el plan rechaza (y `inspect_document` informa) `path_cells`. Sin paths, `budget-v4` coincide con `budget-v3`. Cada `dither` (`budget-v5`, ADR-025) se pinta como dos fills que reevalúan su máscara `M` (caja `Bm`): cuesta `2·(visitas(M) + 4·área(Bm))` visitas y `bytes(M) + área(Bm) + 8·(ancho(Bm)+alto(Bm)) + N·ancho(Bm) + 4096` bytes, y el recurso `operations` compara con `max_operations` los fills rasterizados (2 por `dither`; `CostEstimate.fills` y `BudgetReport.fills`, que es el `estimated` de ese recurso en `exceeded`), mientras `operations` sigue contando operaciones del documento; su `origin` se comprueba contra la coordenada máxima. Sin `dither`, `budget-v5` coincide con `budget-v4`. Cada `outline` (`budget-v6`, ADR-027) es un fill que reevalúa su máscara `M` (caja `Bm`) sobre la caja de trabajo `X` (`Bm` crecida `w` y recortada si es `outer`, `Bm` si es `inner`); con `P = (ancho(X) + 2w + 1)·(alto(X) + 2w + 1)` cuesta `visitas(M) + 16·P` visitas y `bytes(M) + área(Bm) + morphology_bytes(X, w) + 2·área(X)` bytes (`morphology_bytes` = `2·área + 4·P + 4·área + 12·min(P, 8192) + 4096`, incluidos los búferes de iteración de NumPy); con máscara vacía, sólo el coste de `M`. Sin `outline`, `budget-v6` coincide con `budget-v5`. Cada banda `i` de un `shade` (`budget-v7`, ADR-028) es un fill que evalúa su máscara `Mi` (caja `Bi`) y pliega cada máscara posterior `Mj` cuya caja la toca: cuesta `visitas(Mi) + 4·área(Bi) + Σ (visitas(Mj) + área(Bi))` visitas y `área(Bi) + max(bytes(Mi), bytes(Mj)…) + 8192` bytes, más 24 576 si pliega alguna (objetos y búferes de iteración de NumPy medidos); una banda vacía no cuesta nada, la operación suma visitas, su pico es el de la banda más cara y `operations` cuenta un fill por banda. Sin `shade`, `budget-v7` coincide con `budget-v6`. Cada banda `i` de un `material` (`budget-v8`, ADR-030) se pinta como un fill por paso de su receta: cada uno cuesta lo de la banda de `shade` más `C·(64·k + 2) + 3·área(Bi)` visitas (`C` celdas de la caja, `k` canales de hash) y su pico es el mayor entre el de la banda y `2·área(Bi) + 5·C + filas_celda·ancho(Bi) + 8·(ancho(Bi) + alto(Bi)) + 16 384` bytes; `operations` cuenta bandas × pasos y su `origin` se comprueba contra la coordenada máxima. Un `selective_outline` cuesta el anillo de `outline` más un fill base (que pliega los tramos que tocan su caja) y un fill por tramo sobre la intersección de su caja con la del anillo; `operations` cuenta `1 + tramos`. Sin ellas, `budget-v8` coincide con `budget-v7`; elevar un presupuesto exige `RenderLimits(host_override=True)`. API puede bajar límites; elevarlos requiere configuración explícita de la aplicación anfitriona, nunca el documento no confiable. Deadline cooperativo entre operaciones es defensa adicional; un servicio expuesto usa proceso aislado y límites del SO para detener una llamada nativa larga.

Imports Pillow verifican dimensiones, límites de descompresión, modo/frames y perfil antes de decode completo; no desactivar globalmente sus protecciones. Assets sólo bajo raíz resuelta y con digest coincidente. Los errores no filtran rutas sensibles. El threat model incluye agotamiento de memoria/CPU, zip slip/bombs, referencias cíclicas, contenido desconocido y comandos de edición inválidos. Secretos y credenciales no se guardan en documentos ni repositorio.

## 21. Testing y regresiones visuales

Pirámide: unit tests de reglas exactas; propiedades de inmutabilidad, límites e idempotencia de normalización; integración documento→render→export→decode; seguridad con entradas hostiles; corpus visual y revisión artística. Fixtures pequeñas permiten verificar píxeles manualmente, no copiar la salida de la implementación como oráculo.

Golden maestro compara RGBA y dimensiones exactamente. Fallo genera expected/actual/diff PNG, bbox, conteo, digest y manifest de entorno. Un render estándar no tiene tolerancia perceptual; SSIM y métricas perceptuales sólo complementan revisión de cambios deliberados. Actualizar baseline requiere fuente del cambio, diferencia visible y aprobación del responsable de revisión; no ejecutar actualización automática en CI ni esconder regresiones aceptando todo.

Determinismo: procesos nuevos, PYTHONHASHSEED diferente, caché on/off y matriz macOS/Linux/Windows con Python soportado. Integración comprueba instalación de wheel fuera de `src`, recursos incluidos y paquete tipado. Markers previstos `visual`, `slow`, `security`, `benchmark`; ausencia inicial de goldens no se presenta como QA del motor. Inicialización valida sólo tooling, dependencias y planificación.

## 22. Rendimiento y optimización

Objetivos iniciales a medir, no resultados actuales: sprite 128×128 con 32 capas/500 rects en <=100 ms mediana de render caliente; 16 frames de igual complejidad <=2 s; pico de memoria del proceso <=256 MiB para ese corpus. Máquina de referencia se registra con CPU, OS, Python, lock y commit. Medir 5 warmups y 30 muestras con mediana/p95, sin I/O en el tramo de render. Presupuesto obligatorio de seguridad sigue vigente aunque el objetivo de latencia no se alcance.

Medir antes de vectorizar. Recortar máscaras a bbox, reutilizar buffers internos sin alias público, renderizar frames en streaming, caché LRU limitada por bytes y invalidación por digest de dependencias. Evitar arrays de tamaño lienzo por cada operación cuando no se necesiten. No añadir GPU, multiprocessing ni JIT sin benchmark que justifique complejidad y demuestre determinismo. CI de PR detecta cambios funcionales; benchmarks son informativos hasta estabilizar runner y umbrales relativos (regresión >20% investigada con repetición controlada).

## 24. Criterios de aceptación

La trazabilidad debe asignar a cada requisito un issue, una prueba/evidencia y fase. MVP estático aceptable: instalar wheel limpio, validar JSON, render de primitivas con paleta/capas, igualdad determinista RGBA, exportar PNG que decodifique igual y rechazar entradas que excedan presupuesto. No afirmar calidad profesional por pasar tests de rasterización.

Producto completo aceptable: además, regiones semánticas y ediciones atómicas; guardar/cargar sin cambios de píxel; undo/redo; corpus artístico revisado; animaciones con tiempos y pivotes consistentes; atlas reversible; GIF con pérdidas explícitas; informes de QA accionables; límites de recursos probados; benchmarks publicados; CI de plataforma; guía de agentes y compatibilidad versionadas. Cada issue añade ejemplos observables específicos; ninguno se cierra con sólo «funciona».

Inicialización aceptable: MOANA.md cubre las 25 secciones; package importable sin engine; lock resuelto realmente; venv y herramientas instaladas; lint/typing/tests/build/checks verdes; siete skills validadas; instrucciones operativas; backlog completo sin ciclos ni requisitos huérfanos; integraciones y capacidades distinguen instalado, configurado y pendiente.

## 25. Definition of Done

Para cada módulo: alcance del issue cumplido, contrato público documentado, tipos completos, errores/presupuestos cubiertos, sin globales mutables, pruebas positivas y negativas significativas, determinismo comprobado, revisión de diffs/goldens cuando aplique, `uv run python scripts/validate.py` verde, docs/ejemplos/trazabilidad actualizados y limitaciones comunicadas. Dependencias nuevas tienen razón técnica y lock revisado.

Para release: todo lo anterior, wheel/sdist instalables, matriz de CI verde, corpus y rúbrica revisados, migración probada, threat model actualizado, presupuesto de rendimiento medido y changelog con versiones de schema/renderer. Publicación de paquetes, creación de repos remoto o envío de issues a terceros son pasos separados de esta preparación; no se inventa que ocurrieron. La licencia de distribución se decidirá con el propietario antes de publicar; los ejemplos creados deberán registrar procedencia.
